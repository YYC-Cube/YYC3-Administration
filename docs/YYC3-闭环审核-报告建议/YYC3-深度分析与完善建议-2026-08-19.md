## 1. 执行摘要

### 1.1 总体评价

项目呈现典型的 **"AI 辅助快速堆料"特征**:功能面极广(41 个页面)、单文件注释规整、类型安全基础尚可(strict 模式、全项目仅 34 处 `any`、零 `@ts-ignore`)、README 与文档体系完备。但工程内核薄弱,与 README 宣称的 "Enterprise Management Platform" 存在明显差距:

| 维度     | 评价                                                                                                   | 关键证据                                                       |

| E2E / CI | 🟢 绿(P0 修复后):E2E 52 通过/0 失败(1 flaky),PR 亦运行 E2E;**修复前** main CI 自 2026-07-16 持续失败   | 修复前根因:E2E 无登录步骤+引导遮罩拦截点击+空转断言(见 2.3 节) |

### 1.2 Top 风险(按优先级)

1. **🔴 高 — main 分支 CI 持续失败 22+ 天且未被察觉**:E2E job 在 push 到 main 时全部失败(最近两次 push:2026-07-16、2026-07-28 均 `e2e in 13m ✗`);PR 上的绿色徽章是假象,因为 E2E 配置了 `if: github.event_name == 'push'` 在 PR 上跳过。README 的 "864/864 Tests" 徽章与真实状态不符。
2. **🔴 高 — E2E 测试体系结构性失效**:**全部 5 个 E2E spec 都没有登录步骤**,而应用有登录墙(AuthProvider 未认证时渲染 LoginScreen),62 例中 55 例因 `app-container` 不可见而失败/超时(实测:7 通过 / 43 失败 / 12 超时);"通过"的 7 例中多数是**空转测试**——断言全部包裹在 `if (await xxx.isVisible().catch(() => false))` 条件里,应用根本没渲染也能通过。
3. **🔴 高 — 无服务端认证的"管理平台"公网部署**:`useAuthStore` 全套认证状态在浏览器 localStorage,首次登录自动播种 `admin/admin123` 账户,且登录页明文展示该密码。任何访客可获管理员权限。
4. **🔴 高 — 用户 API Key 明文存 localStorage + 生产直连 AI API**:代理端点仍是占位符 `'__PROXY_BASE_URL__'`,浏览器持 key 直连 OpenAI/Anthropic/DeepSeek。
5. **🔴 高 — 伪加密**:硬编码 `APP_SECRET` 编译进 bundle,配合 sessionStorage 盐,"加密存储"对任何能打开 DevTools 的人可完整还原;密码哈希为无盐 SHA-256。
6. **🔴 高(性能/体验)— 代码分割完全失效**:`preload-fix.tsx` 同步导入全部页面 + 单一 vendor chunk,首屏需下载约 2.4MB JS。
7. **🟡 中 — 死代码与死依赖体量惊人**:约 8,000–12,000 行零引用代码 + 10+ 个零使用 npm 依赖(含整套 MUI 7)。
8. **🟡 中(工程)— 本地质量门失效**:husky 目录无任何用户钩子,`lint-staged` 配置永远不会执行;lint 脚本以 `--max-warnings 320` 制度化容忍存量告警。

### 2.3 E2E 实测:结构性失效(本次审计最重要发现)

本地实测结果(与 CI 一致):**62 例中 7 通过 / 43 失败 / 12 超时**,exit code 1。

**失败分布**:

| spec                        | 用例数 | 结果                                                 |
| --------------------------- | ------ | ---------------------------------------------------- |
| chat-workflow.spec.ts       | 10     | 全部超时(beforeEach 等 `app-container` 60s 超时)     |
| developer-workspace.spec.ts | 28     | 全部失败(`[data-testid="app-container"]` 10s 不可见) |
| navigation-flow.spec.ts     | 6      | 1 失败 + 2 超时 + 3 通过(空转,见下)                  |
| window-bar-dnd.spec.ts      | 14     | 全部失败(同根因)                                     |
| settings-flow.spec.ts       | 4      | 全部"通过"(空转,见下)                                |

**根因链**(三层问题叠加):

1. **E2E 没有认证前置**:`auth-context` 在未认证时渲染 LoginScreen,而 5 个 spec 的 beforeEach 都只 `page.goto('/')` 后直接等 `[data-testid="app-container"]`——登录墙之后的应用容器永远不会出现。没有任何 spec 执行登录、注入会话 localStorage 或使用 storageState 夹具。
2. **"通过"的用例是空转测试**:settings-flow 与 navigation-flow 的断言全部包裹在 `if (await locator.isVisible({timeout}).catch(() => false))` 中(settings-flow.spec.ts:14,17,24 等)——条件不满足时测试体静默跳过,应用根本没渲染也能通过。这类测试提供了虚假信心,比失败更有害。
3. **CI 结构掩盖了问题**:ci.yml 的 e2e job 条件为 `if: github.event_name == 'push'`——**PR 上从不出 E2E 结果**(Dependabot PR 全绿),只有 push 到 main 才跑,而 main 上连续失败:2026-07-16(3af578b 前后)与 2026-07-28 两次 push 的 e2e job 均为 `✗`(13m 运行)。README 的 "Tests 864/864" 徽章口径与 main 实际状态不符。

**修复方向**(见 7.1-P0):

- 建立 Playwright 全局 setup:登录一次(`page.fill` 账密或直接写入 `yyc3_auth` localStorage)并导出 `storageState`,所有 spec 复用;
- 更彻底的方案:提供 `VITE_E2E=1` 环境变量旁路登录墙(仅测试构建生效);
- 消灭空转断言:删掉 `.catch(() => false)` 包裹的条件式断言,改为真实断言 + 合理超时;`waitForSelector(...).catch(() => {})` 这类"吞错等待"必须移除;
- CI 策略调整:E2E 至少在 PR 上跑 chromium 单项目(`--project=chromium` 已是 CI 现状,去掉 `if: push` 限制),避免 main 长期红灯无人察觉。

### 2.4 测试体系其他观察

- 单测质量较好:ai-proxy-service 35 例、secure-storage 11 例、auth 等核心模块有真实断言;但 41 个业务页面中绝大多数无直接测试,3,037 行的 number-database、2,736 行的 task-board-page 均为零覆盖。
- E2E 配置本身合理:5 浏览器项目、trace/video 仅失败保留、webServer 自动拉起 dev(端口 3171 已与 dev 脚本对齐);近期 4 个 fix commit 修过端口/networkidle/选择器,但都没触达"无登录步骤"这一根本问题。
