## 二、路线选型（提示词 P1 的决策输入，先给结论）

| 方案             | 构成                                                                 | 优点                                                         | 缺点                                     | 适用场景                                  |
| ---------------- | -------------------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------- | ----------------------------------------- |
| A. Supabase 激活 | 激活既有 0001 + 补业务表 + PKCE                                      | 复用存量资产、零运维、PostgREST 天然参数化、RLS 行级安全白送 | 平台锁定、国内延迟、复杂查询与队列能力弱 | **数据面 + 认证面**（最快闭环 F-09/F-05） |
| B. 自建轻后端    | Node(Hono/Fastify) + PostgreSQL + Prisma/Drizzle，容器走既有 GHCR 线 | 完全可控、可承载 AI 网关/定时任务/Webhook、无锁定            | 运维面扩大（备份/监控/加固）、周期长     | **AI 代理网关 + 集成面**                  |
| C. 本地 Dexie    | IndexedDB 本地库 + JSON 导出                                         | 离线可用、零后端、隐私最优                                   | 多端不同步、企业协作弱、与可观测目标冲突 | 离线缓存层（可作为 A/B 之上的体验增强）   |

**推荐：双轨分阶段（A → B → C 融合）**——

- **阶段一（A）**：激活 Supabase 数据面与认证面，清偿 F-05/F-09，最快拿到真实闭环；
- **阶段二（B）**：自建 AI 网关轻后端（承接 VITE_AI_PROXY_URL 的正式实现，服务端密钥化）；
- **阶段三（C）**：Dexie 作为离线缓存 + 断网兜底，与云模式经 feature flag 双轨并存。
  理由：每一阶段独立可上线、可回滚；存量资产（0001 migration/RLS 设计）只在 A 路线被复用，弃之可惜；AI 网关天然不属于 BaaS 能力圈，B 是必然。

## 三、提示词闭环大纲（12 节点链路）

> 使用方式：按序投喂；每节点提示词都应附带「上下文输入」栏列出的文件/结论。
> 每节点产出物合入 main 须过既有 CI 七门；🔒 标记 = 硬安全约束（写进每条提示词，不可省略）。

### P0 · 需求与数据边界冻结

- **目标**：盘点哪些模块从 mock/本地态转真实数据，输出《数据清单与隐私分级表》
- **上下文输入**：nav-config / features 十域清单、F-09 审计章节、`.env.example`
- **提示词骨架**：「逐模块盘点 YYC3-Administration 的数据实体与读写路径，区分【演示数据 / 本地持久化 / 需云端】，输出数据清单（实体、属主、敏感级 P0-P3、读写频次、保留策略），并冻结一期范围……」
- **DoD**：数据清单表 + 一期范围签字；🔒 敏感级 P0（凭据/密钥类）明确标注「永不上前端」
- **产出物**：`docs/backend/P0-DATA-INVENTORY.md`

### P1 · 架构决策复核

- **目标**：以 §二 为输入，重新裁定 A/B/C 与阶段切分（决策可逆性优先）
- **提示词骨架**：「对 Supabase 激活 / 自建轻后端 / 本地 Dexie 三路线做加权评分（成本 30/速度 25/可控 20/风险 15/演进 10），引用 CHANGELOG 1.0.4 的旧决策并给出维持或推翻的理由链……」
- **DoD**：决策记录 ADR-0001（含推翻 1.0.4 P3 决策的理由链与回退条件）
- **产出物**：`docs/backend/ADR-0001-backend-route.md`

### P2 · 数据建模与迁移 🔒

- **目标**：一期实体 ER 模型 + 迁移文件（Supabase SQL）+ RLS 策略全集
- **上下文输入**：0001 迁移（profiles/user_settings 范式：uuid 属主、`auth.uid() = id`、角色 check）、P0 数据清单
- **提示词骨架**：「基于 0001 迁移的范式续写 0002+ 迁移：全部表启用 RLS 且默认拒绝，策略只放行 `auth.uid()` 属主；角色列沿用 check('admin','manager','agent','viewer')；🔒 所有动态查询一律参数绑定，禁止任何字符串拼接/format/f-string 组装 SQL……」
- **DoD**：迁移可 `db push` 亦可**向下回滚**（每个迁移配 down 脚本）；RLS 越权矩阵测试通过
- **产出物**：`supabase/migrations/0002_*.sql` + `docs/backend/ER.md`

### P3 · 认证与权限（F-05/F-19 清偿）🔒

- **目标**：PKCE 真实认证替换演示态；GHOST_ACCOUNTS 降级为「仅本地演示模式且显式声明」；注册限流
- **上下文输入**：auth-context.tsx、useAuthStore、0001 角色枚举、F-05 审计条目
- **提示词骨架**：「设计 Supabase PKCE 认证接线：会话持久化与刷新、角色→前端权限映射（viewer 最小权限默认）、演示账号体系与真实认证的互斥开关（GHOST_MODE 仅 DEV）；同时设计注册限流（IP+邮箱双维）与验证码接入口…… 🔒 凭据只经环境变量注入，源码/测试不得出现可用凭据字面量」
- **DoD**：越权测试矩阵（viewer 试写 admin 资源必败）通过；生产构建 grep 无 GHOST 硬编码激活路径
- **产出物**：`src/services/auth-service.ts` + 测试

### P4 · API 契约与类型共享

- **目标**：单一契约源（OpenAPI 或 zod schema 包），前后端类型同源
- **提示词骨架**：「为一期实体定义 zod schema + 错误码表（业务码/HTTP 码映射），生成共享类型包 @yyc3/api-contract，前端 supabase-js 调用与后端路由同源消费……」
- **DoD**：契约包发布 workspace；前端类型零手写漂移；错误码全覆盖
- **产出物**：`packages/api-contract/`（或 docs/契约文档）

### P5 · 服务端实现（阶段二 B 线主体）🔒

- **目标**：AI 网关轻后端：/ai-proxy 转发（密钥服务端化）、健康检查、限流、审计日志
- **提示词骨架**：「实现 Hono/Fastify 服务：①POST /ai-proxy——从环境变量读上游密钥，按 provider 白名单转发，请求体 zod 校验；②GET /healthz 就绪探针；③令牌桶限流；④结构化审计日志（谁在何时调了哪个模型，不含密钥本体）。🔒 全部密钥环境变量注入；Dockerfile 复用容器线规范（多阶段 + pnpm 钉扎 + 非 root 运行）」
- **DoD**：容器经 GHCR 线发布；/healthz 进 uptime 监控；注入攻击用例（SQL/提示注入）通过
- **产出物**：`server/` 目录 + GHCR 镜像

### P6 · 前端接线与降级 🔒

- **目标**：SPA 接云模式：supabase-js 客户端、feature flag（本地模式 ↔ 云模式）、CSP 更新
- **上下文输入**：csp-harden 插件（connect-src 动态注入机制）、`.env.example`
- **提示词骨架**：「为应用加数据源开关：未配置 VITE_SUPABASE_URL 时完全回落本地模式（现状零破坏），配置后激活云读写；CSP connect-src 经既有 csp-harden 机制注入 Supabase 域；所有数据调用经 P4 契约类型；🔒 anon key 属公开凭据可内联，service_role 永不进前端」
- **DoD**：双模式 E2E（本地/云）皆绿；未配置环境零行为变化（回归）
- **产出物**：`src/services/data-source.ts` + 开关 UI

### P7 · 测试与越权矩阵 🔒

- **目标**：RLS 越权矩阵、注入用例、迁移回滚演练进 CI
- **提示词骨架**：「生成四角色 × CRUD 越权测试矩阵（匿名/viewer/agent/manager/admin 对每表每操作断言 200/403）；SQL 注入用例集（单引号/注释/Union/时间盲注）验证参数绑定面；迁移 up/down 各演练一次……」
- **DoD**：矩阵全绿入 CI；回滚演练留档
- **产出物**：`tests/security/` + CI job

### P8 · CI/CD 与迁移门

- **目标**：迁移纳入发布门；后端容器线复用 GHCR + docker-smoke
- **提示词骨架**：「扩展 CI：迁移 dry-run 门（对影子库执行 up/down）；Deploy 前置迁移任务（失败即阻断发布）；服务端镜像走 docker-release.yml 同款 tag 策略……」
- **DoD**：红迁移 = 不发布；发布手册补后端章节
- **产出物**：workflow 变更 + runbook §7

### P9 · 可观测与告警

- **目标**：后端日志/慢查询/错误率接入既有监控体系
- **提示词骨架**：「为后端定义三金线指标（p95 延迟/错误率/上游配额水位），接入既有 uptime.yml 家族：新增 api-alert label 的告警 issue 自动管理；Sentry 服务端 SDK 与前端共用 release 版本链……」
- **DoD**：三指标有告警规则；演练一次人为故障验证告警可达
- **产出物**：monitoring 扩展 + 告警验收记录

### P10 · 灰度与切换

- **目标**：真数据切换可分批：内部 → 演示域 → 生产；随时可退回本地模式
- **提示词骨架**：「设计切换灰度：数据源开关按环境分级生效（dev 全量/生产仅白名单会话）；写好『云回本地』的数据导出脚本（JSON 出口，呼应 Dexie 三阶段路线的同步出口设计），保证任何时点可整体退回……」
- **DoD**：灰度演练一次；回退演练 ≤15 分钟
- **产出物**：灰度手册章节

### P11 · 验收终审（复用六维度闭环标准）

- **提示词骨架**：「对本后端一期做生产闭环终审：链路完整性/功能质量/性能容量/安全合规/运维可观测/合规归档六维度，按 2026-11-01 终审报告格式输出校验表与遗留分级……」
- **DoD**：终审报告归档 docs/YYC3-闭环审核-报告建议/

### P12 · 迭代回流

- **目标**：终审遗留 → 下一轮 P0 输入，闭环重启
- **约定**：每轮终审遗留清单直接成为下一版 P0 的「上下文输入」，形成永久闭环

## 四、横切约束（每条提示词的固定尾缀，逐字附加）🔒

```text
安全硬约束（违反即验收不通过）：
1. 所有 SQL/查询语句中，外部输入必须使用参数绑定（Prepared Statement /
   PostgREST 过滤器 / ORM 参数化），禁止字符串拼接、format、f-string 组装 SQL。
2. 凭据（service_role、上游 API Key、DSN 之外的私密项）只从环境变量或密钥服务读取；
   源码、示例、测试、文档一律不得写入可用凭据字面量。
3. RLS/权限默认拒绝：新表新端点先默认不可访问，再按需放行属主。
4. 每个迁移必须配对向下回滚脚本；每个新端点必须有越权与注入测试。
5. 产出合入 main 必须通过既有 CI 七门（覆盖率棘轮只升不降）。
```
