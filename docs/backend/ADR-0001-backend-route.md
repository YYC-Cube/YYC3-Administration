# 🏛️ ADR-0001 · 后端与数据库路线决策（P1）

> ⚠️ **部分取代（2026-11-04）**：用户裁定不引入 Supabase 项目 → A 线载体作废，
> 由 [ADR-0002](./ADR-0002-supabase-free-route.md) 接替：B 线（Node 自托管轻后端）
> 提前至 M1 并吸收原 A 线数据面范围（SQLite 方言、JWT 认证、RLS 等价物改为唯一
> 数据访问模块）。本文的评分框架、C/B 线定位与回退思想仍然有效，保留为决策链存档。

> 闭环大纲节点 P1 交付物。输入：P0《数据清单与隐私分级表》（frozen-signed）+
> CHANGELOG 1.0.4 旧决策 + 09-26《05-本地数据库替代方案分析》。
> 加权评分维度与权重（大纲 §二）：成本 30 / 速度 25 / 可控 20 / 风险 15 / 演进 10。

## 一、决策状态

**ACCEPTED（2026-11-02）——推翻 CHANGELOG 1.0.4（2026-09-26）「放弃 Supabase 激活，
改为本地数据库（Dexie）三阶段」的路线决策**，改为：

> **双轨分阶段：A 线（Supabase 激活）于 M1 立即启动；B 线（自建 AI 网关）维持 M3
> 规划；C 线（Dexie 离线层）降级为远期可选项，Dexie 专项（原三阶段）取消。**

前置条件：用户提供 Supabase 项目凭据（`VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`
写入本地 `.env`，🔒 勿入库）。

## 二、旧决策回顾与推翻理由链

1.0.4 旧决策的原始语境（2026-09-26）：当时 Supabase 项目未配置、P3 数据面以演示
优先、避免引入外部依赖——「放弃激活」是**当时凭据缺失下的合理止损**，而非对 A 线
技术价值的否决。

推翻依据（P0 实测新证据）：

| #   | 新证据                                                                                               | 对旧决策的否定强度                     |
| --- | ---------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 1   | `user-data-sync.ts` 已实现 `user_settings` 双向同步且 F-01 修复时已挂载——激活即通，零新开发          | 直接推翻「改本地需另起炉灶」的成本假设 |
| 2   | 0001 迁移（profiles/user_settings + RLS 属主）已备且范式正确                                         | 推翻「数据面从头建设」假设             |
| 3   | F-05 清偿（认证替换）的最短路径 = Supabase PKCE；本地 Dexie 无法提供认证/多端/服务端密钥三大后端刚需 | C 线在刚需面前结构性缺位               |
| 4   | 真实数据闭环仅 25-30%（F-09），业务正等待数据面；本地路线无法闭环「多端一致」                        | 时间价值反向加强 A 线                  |
| 5   | 代码已内建数据源双模门控（未配置即回落本地）——A 线的回退成本趋近于零                                 | 消除「引入即绑定」的风险顾虑           |

## 三、三路线加权评分（5 分制 × 权重）

| 维度（权重） | A · Supabase 激活                      | B · 自建轻后端                 | C · 本地 Dexie          |
| ------------ | -------------------------------------- | ------------------------------ | ----------------------- |
| 成本（30）   | 5（零新开发，激活即通）→ **30**        | 2（周级开发+运维面）→ 12       | 4（本地三阶段开发）→ 24 |
| 速度（25）   | 5（天级上线）→ **25**                  | 2 → 10                         | 4 → 20                  |
| 可控（20）   | 3（平台锁定/额度）→ 12                 | 5（完全可控）→ **20**          | 4 → 16                  |
| 风险（15）   | 4（RLS+PKCE 成熟，回退零成本）→ **12** | 3（安全面自担）→ 9             | 4 → 12                  |
| 演进（10）   | 3（复杂查询/队列弱）→ 6                | 5（网关/任务/Webhook）→ **10** | 1（不解决后端刚需）→ 2  |
| **合计**     | **85**                                 | 61                             | 74                      |

**评分结论**：A(85) > C(74) > B(61)。但三者非互斥——最优解为**时序组合**：
A 立即（数据面+认证面）→ B 按需（M3，AI 网关是 B 的不可替代理由：服务端密钥持有）
→ C 远期可选（离线增强，非本期）。

## 四、分阶段执行裁定

| 阶段           | 路线 | 内容                                                                                                           | 出口                             |
| -------------- | ---- | -------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| **M1**（启动） | A    | 激活 Supabase：M1-0 PKCE 认证（F-05 清偿）→ M1-1 settings 同步（激活即通）→ M1-2 AI 配置云端化 → M1-3 聊天会话 | 真实登录 + 三类数据云闭环        |
| **M2**         | A    | 契约（P4）+ 十域业务表逐域建模（P2 续）+ 双模接线（P6）                                                        | 业务数据闭环                     |
| **M3**         | B    | AI 网关轻后端（服务端密钥，退役前端带 key 直连）                                                               | `VITE_AI_PROXY_URL` 指向自有网关 |
| **远期**       | C    | Dexie 离线层（可选）                                                                                           | 断网可用性增强                   |

## 五、回退条件与回滚机制

**回退触发条件**（任一满足即启动评审，连续两月未缓解则执行回退）：

1. Supabase 免费额度连续两月不敷实际用量且不愿付费；
2. 国内访问 p95 延迟 > 2s 且 CDN/代理方案无法改善；
3. 合规要求数据驻留地无法满足；
4. 平台价格/政策剧变影响可用性。

**回滚机制**（均已内建/低成本）：

- 数据源双模门控（`VITE_SUPABASE_*` 缺省即回落本地模式）——一键降级；
- P0 §六 JSON 打包导出口——云端数据可整体退回本地，保证任何时点可逆；
- 0001 迁移向下脚本（P2 节点产出）。

## 六、影响面

  ai-model-store/chat-session 增加云端通道（M1-2/3）。

- 🔒 横切约束继续生效（参数绑定/凭据环境变量/RLS 默认拒绝）。
