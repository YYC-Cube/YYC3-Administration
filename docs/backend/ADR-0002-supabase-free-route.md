# 🏛️ ADR-0002 · 无 Supabase 的无损替代路线（P1 修订）

> ⚠️ **修订（2026-11-10）**：本机 PG 15 主库（localhost:5433）实测在位 → §四数据
> 载体由 SQLite 修订为 **PostgreSQL 15**（详见 [ADR-0003](./ADR-0003-pg15-dialect.md)：
> drizzle 方言切换、其余裁定不变）；§五部署档位定为「①本机模式（后端与主库同主机）」。

> 触发：用户裁定**不引入 Supabase 项目**（2026-11-04）。本文部分取代 ADR-0001——
> 其「A 线 = Supabase 激活」载体作废，B/C 线定位吸收合并；评分框架与回退思想沿用。

## 一、「无损」硬约束（判定基准 = P0 冻结的 M1 范围）

任一路线必须完整达成，缺一即「有损」：

| #   | 需求                                                 | 来源     |
| --- | ---------------------------------------------------- | -------- |
| R1  | 真实认证替换 F-05（注册/登录/会话，密码不可逆存储）  | M1-0     |
| R2  | settings 云同步（用户级单文档，并发写可解）          | M1-1     |
| R3  | AI 模型配置云端化（**静态加密存储**，优于 RLS-only） | M1-2     |
| R4  | 聊天会话云端化（多行增量，50×200 护栏）              | M1-3     |
| R5  | 多端一致（同一账号跨设备）                           | P0 §五   |
| R6  | 数据可逆（JSON 导出整体退回本地）                    | P0 §六   |
| R7  | P0 红线：凭据服务端持有（M3 AI 网关不可再拖）        | 隐私分级 |
| R8  | 🔒 参数绑定/RLS 等价物（逐属主隔离）/凭据仅环境变量  | 横切约束 |
| R9  | 不引入第三方 SaaS 账号（本轮新增约束）               | 用户裁定 |

## 三、加权评分（沿用 ADR-0001 权重：成本30/速度25/可控20/风险15/演进10）

> 关键校准：ADR-0001 给 B 线「成本 2、速度 2」基于「全量业务建模」假设；P0 已把
> 范围收窄到 **4 类实体**（auth/settings/ai-configs/chat），且管线资产（GHCR 镜像线、
> docker 冒烟、uptime 监控、compose）全部可复用 → N 的成本/速度显著上调。

| 维度（权重） | N · Node 轻后端                                       | P · PocketBase          | W · CF Workers             |
| ------------ | ----------------------------------------------------- | ----------------------- | -------------------------- |
| 成本（30）   | 3（4 实体 + 管线复用，约一周）→ **18**                | 4（两三天配置）→ 24     | 3（Workers+D1 学习面）→ 18 |
| 速度（25）   | 3 → **15**                                            | 5 → 25                  | 3 → 15                     |
| 可控（20）   | 5（代码/数据/部署全自有）→ **20**                     | 4（Go 二进制黑盒）→ 16  | 3（平台依赖）→ 12          |
| 风险（15）   | 4（权限自担→以单一数据访问模块+越权测试约束）→ **12** | 4（声明式规则成熟）→ 12 | 3（D1 成熟度/冷启动）→ 9   |
| 演进（10）   | 5（M3 网关同栈，zod 契约前后端同源）→ **10**          | 2（网关仍另起）→ 4      | 4 → 8                      |
| **合计**     | **75**                                                | 81                      | 62                         |

**评分辨析**：P(81) > N(75)，但 P 在 **R7 上有损**——PocketBase 不能承载 AI 代理，
M3 仍需独立 Node 网关 → 最终形成「PocketBase + Node 网关」双运行时，运维面反而
高于 N 的单容器；且 N 与既有 TS 全栈/zod 契约/GHCR 管线完全同构。**综合裁定：
N 为主路线**（无损失且长期最简）；P 保留为「若要最快见效」的备选；W 在用户未来
接受外部平台时可作零运维替代；D 维持离线层定位不变。

## 四、决策（ACCEPTED）

> **采用方案 N：Node(Hono) + SQLite(better-sqlite3) 自托管轻后端——ADR-0001 的
> B 线提前至 M1，并与数据面合并为单一服务（一个容器、一个 DB 文件、一份部署）。**

- 架构：`server/` 入 workspace；Hono + zod 校验 + better-sqlite3（**全部查询参数
  化** 🔒）+ drizzle-orm（类型化 schema 与迁移）；认证 argon2id + JWT httpOnly
  Cookie（附 CSRF 策略）；限流令牌桶（顺带清偿 F-19）。
- 端点：`/auth/register|login|logout|me`、`/settings(GET/PUT)`、`/ai-configs CRUD`
  （AES-GCM 静态加密，服务端密钥走 env 🔒）、`/chat/sessions CRUD`、`/export`
  （R6）、`/healthz`（接入既有 uptime 监控）、M3 起挂 `/ai-proxy`（同一服务，
  feature-flag 开关）。
- 权限等价 RLS：**唯一数据访问模块**（所有 SQL 强制携带 `user_id` 作用域，禁止
  业务代码直连 DB）+ 越权测试矩阵（对应大纲 P7）。
- 部署：复用既有管线——GHCR 镜像（docker-release.yml 同款 tag 策略）+ compose
  `server` profile（端口 8787）+ docker-smoke 周冒烟 + `/healthz` 拨测。
- 前端接线：`VITE_API_BASE_URL`（csp-harden 注入 connect-src，同 Supabase 机制）。

## 五、部署前提（唯一新增人工依赖）

**一台常驻主机**（VPS / 家庭服务器 / NAS 皆可，能跑 Docker 即满足）。三档兜底：

1. 有常驻主机 → 按本 ADR 全量执行（默认路径）；
2. 仅家庭内网 → 同栈部署为**局域网模式**（单用户在家多端仍无损，R5 收窄为内网多端）；
3. 均不接受 → 退回评审 W（需接受 CF 账号）或重新冻结 M1 范围。

## 六、回退机制

- 双模门控保持：`VITE_API_BASE_URL` 缺省即回落本地模式（现状零破坏）；
- `/export` JSON 打包 + 前端导入 → 任何时点可整体退回本地；
- SQLite 单文件 = 备份即复制（litestream 可选后续加）。

## 七、对既有文档的影响

- ADR-0001：**部分取代**（A 线载体 Supabase 作废；B 线提前至 M1 并吸收 A 线范围；
  C 线不变；回退思想沿用）。
- 大纲 P2：数据建模目标从 Supabase SQL 迁移改为 **drizzle schema + 迁移
  （SQLite 方言）**，RLS 等价物改为「唯一数据访问模块 + 越权矩阵」，其余不变。
- P3 认证：PKCE → JWT httpOnly Cookie 方案，F-05/F-19 清偿目标不变。

chat_sessions 四实体 + 索引）+ 迁移文件 + 唯一数据访问模块骨架 + 越权测试矩阵草案
